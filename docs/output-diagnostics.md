# Подсказки при Wrong Answer

Диагностика добавляется в `SubmissionDetail.diagnostics` при создании отправки,
получении отправки и получении последней отправки задачи. Она работает поверх
сохранённого результата: `worker/checker.py`, вердикты, очередь и схема базы не меняются.
Отдельных запросов к LLM, внешним API и новых зависимостей нет.

Пример дополнительного поля ответа:

```json
{
  "diagnostics": [
    {"type": "case_mismatch", "message": "Проверьте регистр букв. Заглавные и строчные буквы различаются."},
    {"type": "extra_whitespace", "message": "Проверьте количество пробелов между словами."}
  ]
}
```

## Анализ

`app/services/output_diagnostics.py` получает вердикт, ожидаемый и фактический вывод.
Для любого вердикта, кроме `WRONG ANSWER`, или отсутствующего вывода результат пуст.
Строки длиной от 10 000 символов пропускаются целиком: локальный checker ограничивает
сохранённый вывод этим размером, поэтому нельзя делать выводы по потенциально обрезанной строке.
Оригинальные строки не изменяются.

Анализ перебирает небольшой фиксированный набор комбинаций преобразований копий строк.
Подсказки выдаются, только если комбинация объясняет различие целиком. Выбирается
минимальное количество сообщений, не больше четырёх, без повторяющихся типов:

- `case_mismatch`: регистр букв;
- `extra_whitespace`: лишние, недостающие пробелы и табуляция между словами;
- `edge_whitespace`: пробелы по краям вывода или отдельных строк;
- `line_breaks`: расположение переносов строк;
- `number_format`: разные записи численно равных десятичных чисел;
- `extra_text`: добавленная текстовая подпись перед полным ответом или после него.

Числа распознаются как отдельные токены до 128 символов и сравниваются через точный
`Decimal`, без `float`, округления и допуска. Поддерживается десятичная экспонента;
NaN, бесконечность, запятая и неоднозначные записи пропускаются.
Лишний текст определяется консервативно, сообщение явно обозначает предположение.
При неизвестном различии или пустом выводе специфических подсказок нет.

Существующая проверка игнорирует CRLF/CR и пробельные символы по краям всего вывода.
Поэтому одни только внешние пробелы не приводят к Wrong Answer и не вызывают
диагностику в API. Пробелы внутри отдельных строк могут приводить к Wrong Answer.

## Видимость и интерфейс

Перед анализом API выбирает ожидаемый вывод только открытого теста той же задачи.
Для скрытого, удалённого или чужого теста `diagnostics` остаётся пустым. Клиентские
диагностические сообщения не принимаются как источник подсказок.
Для проверок функций с префиксом `# mca:function-test:v1` анализ отключён:
`actual_output` может содержать сообщение assertion, а не stdout.

При обычном локальном сравнении Wrong Answer теперь сохраняет именно сравнивавшийся
stdout, даже если программа также записала текст в stderr. Вердикт не меняется.
Ошибка диагностического модуля логируется и не мешает API вернуть исходный результат.

Секция «💡 Подсказка» находится внутри существующей карточки результата и использует
её CSS-классы. Она отображается только при Wrong Answer с непустой диагностикой.
Сообщения вставляются через `textContent`; смена диагностики обновляет карточку.

Ограничение существующей архитектуры: режим LOCAL передаёт браузеру весь набор тестов,
включая скрытые, через `/api/tasks/{id}/local-tests`, и сохраняет присланный браузером
`actual_output`. Этот контракт сохранён. Новая диагностика ничего не добавляет
для скрытых тестов, но полная конфиденциальность их содержимого требует серверной
проверки, а не LOCAL.

## Проверки

Пройдены 208 Python-тестов: модуль диагностики, worker, сервис отправок, локальный
Python checker, API отправок и API тестов. Использована отдельная временная
PostgreSQL 16 база с суффиксом `_test`. Docker daemon в среде недоступен;
при импорте worker для unit-тестов отключено автоопределение версии Docker API.
Сами тесты worker используют существующие подставные контейнеры; реальный запуск
контейнера в этой среде не проверялся.

Также пройдены все 66 frontend-тестов, включая четыре новых проверки карточки:
несколько подсказок, безопасный текст, отсутствие секции и обновление диагностики.

```bash
.venv/bin/python -m pytest tests/services/test_output_diagnostics.py \
  tests/worker_tests tests/services/test_submission.py \
  tests/services/test_local_python_checker.py tests/api/test_submission.py \
  tests/api/test_test_case.py -q
node --test tests/frontend/*.test.js
```

Для штатного запуска Python-тестов нужны PostgreSQL из `TEST_DATABASE_URL` и
доступный Docker daemon при импорте существующего worker.
