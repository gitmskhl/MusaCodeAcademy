# Экспорт и полная замена базы

## Подготовка

Один раз после установки этой возможности пересоберите и обновите приложение
и worker. В образ включён PostgreSQL client 17:

```bash
docker compose up -d --build app worker
```

Структура БД для экспорта не меняется. Скрипт предназначен для Linux-сервера
с Bash, Docker Compose v2 (с поддержкой `--wait`), `flock` из util-linux
и конфигурацией этого проекта. PostgreSQL и Redis должны быть запущены.

## Скачать копию

Войдите администратором, откройте `/admin` и нажмите **«Экспорт БД»**.
Браузер скачает один `musacodeacademy_…_UTC.dump`: custom-архив PostgreSQL
со структурой, данными, последовательностями и отметкой Alembic.
Архив содержит в том числе аккаунты и хеши паролей; храните его приватно.
Запросы без входа, от студентов и от заблокированных администраторов запрещены.
Временный файл удаляется после скачивания, в том числе при обрыве соединения.

Изображения из `uploads`, код, `.env`, роли PostgreSQL и содержимое Redis
не входят в дамп. Сохраните и перенесите `uploads` отдельно, сохраняя пути файлов.
Настройки `.env` на каждой машине должны соответствовать её окружению.
Сам экспорт не останавливает сайт. При больших БД увеличьте таймаут reverse proxy:
создание архива может занимать до пяти минут, плюс время скачивания.

## Восстановить локально или на сервере

Поместите файл на нужную машину. Запускайте скрипт **на этой машине**, из
checkout проекта, а не внутри контейнера:

```bash
./scripts/restore-server.sh /полный/путь/backup.dump
```

Введите `RESTORE`, чтобы подтвердить полную замену. Для автоматического запуска:

```bash
./scripts/restore-server.sh --yes /полный/путь/backup.dump
```

Скрипт сам переходит в корень проекта; имя базы и доступ берёт из сервиса
`postgres` в Docker Compose. Пароли не нужно передавать аргументами.
Можно использовать стандартные `COMPOSE_FILE` и `COMPOSE_PROJECT_NAME`, если
на машине несколько окружений. Применяются образы, уже собранные для этого кода.

Последовательность:

1. Проверяет формат и восстанавливает архив во **временную отдельную БД**.
2. Применяет к временной БД миграции из текущего образа и проверяет наличие
   всех столбцов моделей. При ошибке рабочая БД и запущенный сайт остаются на месте.
3. Останавливает app и worker. Сохраняет текущую БД в
   `backups/restore_…/before.dump`; журнал находится рядом в `restore.log`.
4. В одной транзакции переименовывает базы: новая получает рабочее имя,
   прежняя сохраняется под временным именем до успешного запуска.
5. Пересоздаёт только Redis-очередь `submission_queue` по загруженной БД.
   Задания `PENDING` и прерванные `RUNNING` будут проверены заново;
   завершённые решения сохраняются. Остальные ключи Redis не удаляются.
6. Запускает app, ждёт успешной healthcheck и запускает worker.
   Затем удаляет прежнюю БД из PostgreSQL; файл `before.dump` остаётся.

При сбое после переключения скрипт останавливает сервисы, возвращает прежнюю БД,
пересобирает её очередь и возвращает исходно работавшие сервисы. Если это не
удаётся, оставляет сервисы остановленными и сообщает путь к копии и журналу.
Если сбой случился уже после открытия сайта, записи, успевшие попасть в новую БД,
не переносятся в возвращаемую прежнюю БД. Для закрытого окна обслуживания
ограничьте внешний доступ до окончания всех проверок.

Нужен запас дискового пространства для временной базы, прежней базы и дампа.
Старые каталоги `backups/restore_…` автоматически не удаляются: переносите копии
на отдельное хранилище и удаляйте ненужные вручную. Они создаются с приватными
правами и исключены из Git. Нельзя запускать несколько восстановлений одновременно.

## Границы переноса

**Это полная замена, без объединения данных.** Если скачали серверную копию,
редактировали её локально и вернули обратно, более поздние серверные регистрации,
решения и прогресс исчезнут. Чтобы этого не произошло, запретите запись на сервере
на всё время от исходного экспорта до обратной загрузки. Сам скрипт останавливает
сервисы только на время замены; кнопка экспорта режим обслуживания не включает.

При изменении только записей пересборка не нужна. При изменении кода или структуры
БД сначала подготовьте совместимый образ с нужными миграциями. Дамп из более новой
версии кода может не подойти старому образу; это проверяется на временной базе.

Принимайте только собственные доверенные дампы: восстановление исполняет SQL
из архива. Формат и поведение описаны в документации PostgreSQL:
[pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html),
[pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

## Проверка изменений

API и помощник очереди проверяются обычными pytest-тестами
`tests/api/test_database_backup.py` и `tests/services/test_database_restore.py`.
Кнопка: `node --test tests/frontend/admin-database-export.test.js`.

Для сквозной проверки восстановления после сборки образа:

```bash
python3 tests/operations/restore_smoke.py
```

Этот тест создаёт отдельный временный Docker Compose с собственной PostgreSQL
и Redis, проверяет замену, резервную копию, повреждённый архив и откат при ошибке
запуска сайта, затем удаляет своё окружение. Рабочая БД проекта не используется.
