# Проверка Python-задач в браузере

В редакторе задачи (`/admin/steps/{step_id}/task`) настройка «Способ проверки»
выбирает один из двух режимов:

- `local` — Python и тесты выполняются в браузере ученика. Режим по умолчанию.
- `server` — решение поступает в прежнюю очередь Redis и проверяется обработчиком.

## Обновление базы

Перед запуском обновлённого приложения выполните в окружении приложения:

```bash
python -m alembic upgrade head
```

Миграция `b71d9e4a620f` добавляет `tasks.checking_mode` и устанавливает `local`
для **всех существующих задач**, а также как значение по умолчанию для новых.
Для отдельных задач после обновления можно выбрать `server` в админке.
История сдач и ранее сохранённый прогресс сохраняются.

## Как работает локальная проверка

1. После нажатия «Отправить решение» браузер получает все тесты через
   `GET /api/tasks/{task_id}/local-tests`. Нужны авторизация, запись на курс
   и опубликованный курс. Для серверных задач этот маршрут недоступен.
2. Отдельный Web Worker загружает Pyodide **0.27.7 (Python 3.12)** с
   `https://cdn.jsdelivr.net/pyodide/v0.27.7/full/`. Дополнительный npm-пакет
   или сборка фронтенда не требуются. Первый запуск требует загрузки среды;
   её файлы кешируются браузером. При каждой отправке создаётся новый worker.
3. Тесты идут по порядку до первой ошибки. Программа получает вход через
   `stdin`, результат сравнивается со стандартным выводом. Как и на сервере,
   окончания строк нормализуются, пробельные символы по краям игнорируются.
4. Браузер отправляет код и `local_result` в существующий `POST /api/submissions`.
   Сервер сохраняет итоговый статус и число тестов. Для `ACCEPTED` сдача и
   прогресс шага сохраняются в одной транзакции. Redis и Docker не используются.
   Неуспешные сдачи также сохраняются в истории и не сбрасывают прежний прогресс.

Сервер принимает локальные результаты только для задач с режимом `local`.
Он проверяет структуру результата и соответствие количества/идентификатора тестов,
но доверяет результату браузера и не запускает решение повторно.

## Особенности среды

- Скрытые тесты также отправляются в браузер: это необходимо для полной локальной
  проверки. Обычный интерфейс просмотра скрытого теста остаётся закрытым.
- Лимит времени применяется к каждому тесту после загрузки среды. При превышении
  worker завершается; интерфейс страницы остаётся доступным. При уходе со страницы
  проверка отменяется. Сбой загрузки среды не запускает серверную проверку автоматически.
- Вывод ограничен 100 КБ на поток, сохраняемые данные ошибки/вывода — 10 000 символов.
- Жёсткий лимит памяти в браузере не применяется. Настройка памяти относится
  к серверной проверке; Python `MemoryError` отображается как ошибка памяти.
- Используется стандартная библиотека Python, доступная в Pyodide; сторонние пакеты
  автоматически не устанавливаются. Нативные возможности, процессы и модули,
  отсутствующие в WebAssembly, требуют серверного режима.
- Каждый тест получает отдельное пространство переменных. Загруженные Python-модули
  и виртуальная файловая система общие в пределах одной отправки; для задач,
  требующих полного разделения процессов между тестами, выбирайте серверный режим.

## Проверки

```bash
python -m pytest tests/api/test_task.py tests/api/test_submission.py \
  tests/services/test_task.py tests/services/test_submission.py \
  tests/services/test_local_python_checker.py
node --test tests/frontend/local-python-runner.test.js
```

Python-тесты используют выделенную PostgreSQL-базу с суффиксом `_test` согласно
`tests/conftest.py`. Браузерный модуль дополнительно проверен в Chrome с реальным
Pyodide: успешная сдача, неверный ответ, ошибки выполнения и синтаксиса,
бесконечный цикл, бинарные потоки, `SystemExit(0)` и ограничение вывода.
